# Procedural generation and deterministic seeds

Reviewed: 2026-08-29

Procedural generation is authored possibility space, not a replacement for design. Specify what must always be true, what may vary, and how bad outputs are detected before choosing an algorithm.

## Start with the contract

Define inputs, output schema, invariants, quality metrics, performance budget, fallback and reproduction key. Examples of invariants include reachable goal, required resources before locks, bounded difficulty, navigable clearance and maximum generation time.

Generation modes have different constraints:

- **Offline/editor generation:** may be slow, reviewed and baked into source control.
- **Load-time generation:** must be bounded, deterministic and recoverable.
- **Streaming generation:** must be coordinate-stable, asynchronous and memory-bounded.
- **Per-turn generation:** must not create perceptible stalls or unfair hidden changes.

## Determinism model

A seed is only one input. Reproduction also needs generator version, configuration/content version, platform-relevant numeric rules and sometimes the initial PRNG state.

Do not share one global random stream across unrelated systems. Create named streams such as `world_layout`, `loot`, `combat` and `cosmetics`, derived from a root seed and stable IDs. Adding one cosmetic random draw must not change the world or combat sequence.

Avoid iteration orders that are not guaranteed, frame-time-dependent decisions, unversioned data tables and platform-dependent floating-point comparisons in authoritative generation. Store generated output when exact cross-version preservation matters; otherwise store the complete reproduction key.

## Generator pipeline

`constraints → structural layout → connectivity → content placement → validation → repair → decoration → budget check → result/hash`

Use rejection sparingly: an unbounded “reroll until valid” loop can hang. Prefer constructive algorithms, bounded attempts, targeted repair and a known-safe fallback.

## Validation at scale

For every generated result, run cheap structural checks. In CI, sample a fixed seed corpus plus newly randomized seeds and record failures with the complete reproduction key. Measure distributions—not only pass rate—for path length, density, resource timing, difficulty, dead ends and generation cost.

Keep three corpora:

- golden seeds representing important shapes;
- regression seeds for every fixed defect;
- fuzz seeds selected or generated by CI.

Shrinking a failing case to the smallest seed/configuration is valuable, but never discard the original failure artifact.

## Player-facing rules

Expose a seed only if the same seed has a meaningful compatibility promise. State whether updates may change its world. Prevent generation from creating inaccessible content, unwinnable states, flashing patterns, offensive text combinations or extreme performance spikes.
